### [pi-webserver-ansible](https://github.com/justin-garter/pi-webserver-ansible)

This is the infrastructure behind [justingarter.com](https://justingarter.com): a Raspberry Pi 5 (1 GB) serving a static site from a DMZ VLAN behind an OPNsense firewall, reachable from the internet only through Cloudflare on port 443. The firewall admits Cloudflare's published address ranges and nothing else, so the origin can't be reached around the proxy, and the Pi runs its own hand-written default-deny nftables ruleset that limits SSH to two admin sources. TLS uses a Cloudflare Origin CA certificate instead of Let's Encrypt, which removed port 80 and the renewal machinery entirely. The host is an Ansible playbook with vaulted secrets, and the repo carries the operating docs beside it: deploying content, rebuilding from a blank card, routine checks, making changes without locking yourself out, and recovery. The current design came out of a failure. The previous build's only way in was a tunnel the host terminated itself, with no console password, so moving it to a new network left no way in at all. The rebuild added a console break-glass that the playbook refuses to run without, and finished with a reboot and a full run reporting zero changes. One known gap is written down rather than hidden: the 404 jail detects scanners but can't block them behind Cloudflare, so blocking is moving to Cloudflare itself.

### [web-portfolio](https://github.com/justin-garter/web-portfolio)

The content and design history for [justingarter.com](https://justingarter.com), kept separately from the host that serves it. Static HTML and CSS with no build step and no server-side logic, which is what keeps the public attack surface small enough to justify skipping a WAF. The repository carries three successive versions of the site alongside the design options that were considered and dropped, so the progression is legible rather than just the current state. Host configuration lives in [pi-webserver-ansible](https://github.com/justin-garter/pi-webserver-ansible) and is deliberately not here: separating content deploys from host changes means that when the site breaks there is one variable to check instead of two. Deployment is a content push to the DMZ Pi, not a playbook run.

### [mc-client-modpack](https://github.com/justin-garter/mc-client-modpack)

A client-side Minecraft modpack managed as a versioned artifact rather than a folder of jars. Every entry is packwiz metadata carrying a SHA-512 of the file it resolves to, so no binary is committed and the manifest is the source of truth. The pack is carried forward across Minecraft versions rather than rebuilt, with a script that migrates each entry and reports what ported, what has no build yet, and what is worth re-testing, removing nothing on its own. The useful part is the failure handling: the worst breakages here do not crash, they render plain vanilla and look correct, so the documented pass condition is a grep of the launch log rather than the game starting. Three such failures are recorded with the line that gave each one away.

### [ender3-klipper](https://github.com/justin-garter/ender3-klipper)

A Creality Ender 3 V2 converted to Klipper and run as a headless, network-attached print server on a Raspberry Pi 5 (2 GB), using the Klipper/Moonraker/Mainsail stack behind a Caddy reverse proxy. The repository holds a LAN-scoped security assessment of that stack, which found the web UI’s authentication protecting the interface while leaving the printer control API fully exposed. Of five findings, four were remediated with before-and-after probe evidence and one accepted with written rationale rather than quietly dropped. Alongside it are two tuned OrcaSlicer profiles with the calibration data behind every value, and an engineering journal organized by investigation rather than by date. The journal keeps the hypotheses that were eliminated and the conclusions that were retracted, because a record showing only the answers isn’t a record of how they were reached.

### [IT7075-coursework](https://github.com/justin-garter/IT7075-coursework)

Coursework for IT7075C, Applied AI for Cybersecurity, at the University of Cincinnati. Currently one module: environment setup and validation, with notebooks and scripts that check a local Python 3.13 environment and confirm model access before any real work depends on it. Secrets go through a gitignored `.env` with a committed `.env.example` naming the expected variables and no values; keys are never printed, logged or embedded in code. `requirements.txt` deliberately excludes torch, with the reason written in the file: the default PyPI wheel may be CPU-only and a Blackwell card needs a CUDA 12.8 build, so it is installed and verified separately. The instructor’s repository is cloned alongside as read-only reference and never pushed to. This grows through the term.
